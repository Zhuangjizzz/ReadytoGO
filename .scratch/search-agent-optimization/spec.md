Status: needs-triage

## 结论

已经实现“高德搜索 + 本地规则匹配 + 有限相似度召回 + LLM 判断”，也已经实现 AI 行程解析和批量设施分析。尚未实现用户期望的“理解附近搜索意图 → 按需定位 → 搜索 → 数据匹配 → 根据结果继续调用工具”的产品 Agent。

建议先扩展本地召回覆盖，并统一为“候选召回 → 一次批量 LLM 验证 → 服务端合并”；随后把现有查询能力暴露为产品工具，接入可暂停、恢复、有调用预算的单 Agent。沿用千问和原生 OpenAI SDK 的接入配置。

## 1. 先区分三个问题

| 问题 | 输入 → 输出 | 当前负责位置 |
| --- | --- | --- |
| 地点解析 | “故宫东华门” → 一个供用户选择的地图地点及 GCJ02 坐标 | `PlacePicker`、`GET /places/search`、`AmapHttpProvider.searchPlaces` |
| 附近厕所查询 | 已确定起点 + 需求 → 厕所候选、路线和展示分组 | `POST /toilets/search`、`QueryService` |
| 资料身份匹配 | 一个高德厕所 POI → 是否对应本地厕所台账的一条记录 | `Catalog.integrate` / `integrateWithAssistance`、`AiService.matchRecord` |

本地库是厕所台账，不是通用景点库；输入“故宫”时，不应直接把景点与某条厕所记录作身份匹配。应先确定景点起点，再为搜到的厕所 POI 匹配本地设施资料。

## 2. 当前实现

### 2.1 地点输入如何进入地图搜索

普通搜索的链路是：

```text
用户提交地点名称
  → PlacePicker.search()
  → GET /api/v1/places/search?q=...&language=...&city=beijing
  → AmapHttpProvider.searchPlaces(q)
  → 高德 /v5/place/text
  → 返回最多 10 个地点候选
  → 用户选择具体地点或入口
  → 使用该地点坐标发起厕所搜索
```

实现要点：

- 原检索词直接交给高德，限制北京市；普通起点搜索没有厕所类型过滤，也不查询本地台账。
- `language` 在接口接受，但当前没有传给高德，也没有在此路径上调用模型翻译或改写。地点英文输入的匹配能力依赖高德，不能把 AI 行程中的中文改写能力算到普通搜索框上。
- 普通地点搜索返回 `hasMore`，当前公共接口没有分页参数，用户通过更具体的关键词缩小范围。
- 地图手选通过 `/location/resolve` 逆地理编码；当前定位通过浏览器 `getCurrentPosition`，再调用 `/location/convert` 将 WGS84 转 GCJ02 并核对北京行政区。定位由页面逻辑触发，尚未注册成模型工具。

代码依据：[PlacePicker](../../src/client/PlacePicker.tsx#L82)、[客户端接口](../../src/client/api.ts#L46)、[地点接口](../../src/server/routes/core.ts#L29)、[高德文本搜索](../../src/server/providers/amap.ts#L196)、[浏览器定位](../../src/client/LocateButton.tsx#L8)、[坐标转换接口](../../src/server/routes/navigation.ts#L91)。

### 2.2 起点确定后如何找厕所

```text
POST /toilets/search（起点、需求、范围）
  → 读取已有可用位置的本地候选
  → 高德周边厕所 POI 搜索
  → 规则关联本地资料；少数 POI 进入 AI 匹配
  → 为附近少数尚无可用位置的台账记录补做关键词搜索
  → 去重、分批算步行路线
  → 每批一次 AI 设施分析（无效时可再修复一次）
  → 由服务端分组、排序，页面轮询补全结果
```

具体边界来自当前代码，而非理想流程：

| 项目 | 实际行为 |
| --- | --- |
| 普通直线召回 | 10/20 分钟选择分别先查 2/3 公里；最终分钟数由真实步行路线判定 |
| 需要坐便 | 查询普通范围，并另查 5/10 公里扩展范围 |
| 高德周边接口 | `/v5/place/around`，每页 25，`types=200300|200303`，按距离返回；适配器保留北京 `200300`–`200303` 类型 |
| 周边翻页 | 每个范围最多 8 页，并识别重复 POI 集合；本批不足时还会尝试补页 |
| 本地记录反查地图 | 仅有 `sourcePosition` 且处于附近的未定位记录；每次会话最多选 4 条，以“本地名称 + 区县”搜索，每条取最多 5 个 POI |
| 批次 | 每批最多 10 个候选，算路后进行设施分析 |
| 请求节流 | 同一高德适配器最多 5 个在途请求，起始间隔 500ms |
| 返回方式 | 首次最多等待约 150ms 即可返回当前状态；页面继续轮询，并非等待全部任务一次性完成 |
| 等待上限 | 高德实际 HTTP 超时 5 秒，排队上限 90 秒，批次上限 120 秒；不能将 5 秒描述为完整搜索耗时 |

代码依据：[查询启动与反查](../../src/server/query.ts#L275)、[POI 接入及 AI 限额](../../src/server/query.ts#L176)、[批次与分析](../../src/server/query.ts#L475)、[结果排序](../../src/server/query.ts#L669)、[高德适配器](../../src/server/providers/amap.ts#L218)、[配置](../../src/server/config.ts#L2)、[页面轮询](../../src/client/NearbyPage.tsx#L192)。

另有一个应在优化时补齐的预算问题：`maxCandidates=60` 当前只参与 `min(routeBatchSize, maxCandidates)` 的单批填充，没有累计扣减会话已处理候选数。因此它现在不能保证“一个查询最多计算 60 条路线”。分页仍有供应商页数限制，但 Agent 接入需要真正的累计预算。

### 2.3 所谓“数据库”目前是什么

当前使用 `data/generated/catalog.json`，启动时载入内存 `Map`；不是 SQL 数据库，也没有向量数据库。名称关联和附近查询主要遍历内存记录；另有 `poiId → 本地 ID` 索引用于身份复用。

本次只读统计本地导入文件：

| 指标 | 数量 |
| --- | ---: |
| 源记录 | 13,156 |
| 合并重复记录后厕所实体 | 13,124 |
| 有可解析原表坐标 | 7,887 |
| 原表坐标缺失或不可解析 | 5,237 |
| 导入产物已有可用 GCJ02 `position` | 0 |
| 导入产物已有 `poiId` | 0 |

7,887 个原表坐标标为 `crs: unknown`，只作匹配线索。导入代码主动将 `position` 设为 `null`，运行时关联到高德才获得可用于地图、路线的坐标。这不表示线上没有可用厕所：线上可恢复匹配缓存并实时搜索。本地默认位置缓存 `data/generated/matches.json` 本次未发现；未检查线上缓存或线上版本。

### 2.4 目前怎样匹配本地资料

**第一层：规则直接关联。**

已关联的 POI ID 优先复用。对于新 POI，要求区县一致；存在原表位置时须在 800 米内；检查完整道路和门牌冲突。标准化后名称完全相同且距离近，或精确地址/道路门牌相符，才有机会关联。打分为名称相同 +4、地址相符 +3、名称等于地址 +2、距离近 +1；只有最高分唯一时直接合并。缺坐标记录仍可能通过唯一精确地址关联。

这层成功就不经过模型。不能把它描述成“所有匹配先相似度、再 LLM 验证”。代码：[Catalog.integrate](../../src/server/data/catalog.ts#L278)。

**第二层：简易相似度召回 + LLM。**

第一层仍是独立高德记录时，才尝试辅助匹配：

1. 只召回尚未关联的本地记录，且必须同区县、有原表或可用坐标、800 米内。
2. 标准化后拆为去重字符集合，相似度为 `共同字符数 / 两边较大字符集合大小`。这既不是编辑距离，也不是语义向量或 Jaccard 的并集分母。
3. 名称相似度至少 0.4，或地址至少 0.5；仍先排除可识别的道路、门牌冲突。
4. 通过过滤后按距离排序，仅留 4 条；不是综合相似度 Top-K。
5. 将 POI 与这 4 条的名称、地址、区县交给 `AiService.matchRecord`，返回合法候选 ID 或 `null`。坐标、距离与相似度分数没有送给匹配模型。
6. 输出通过 ID、依据字段校验后关联设施、保存规范 ID，原独立 POI ID 仍能解析到该记录。

一个搜索会话最多辅助处理 2 个 POI，逐 POI 请求模型；并非整批 POI 共用一个匹配请求。共用 JSON 方法在内容无效时最多再修复一次，所以每个 POI 通常一次、最多两次模型请求。匹配和空结果有 15 分钟内存缓存；异常也折叠成 `null`，目前难以区分“确实不匹配”与“模型失败”。成功关联可写入位置缓存，缓存带规则版本 2。

代码：[召回](../../src/server/data/catalog.ts#L205)、[辅助关联](../../src/server/data/catalog.ts#L248)、[每会话两条限额](../../src/server/query.ts#L182)、[模型匹配及缓存](../../src/server/ai/service.ts#L189)、[最多一次修复](../../src/server/ai/service.ts#L152)、[持久化](../../src/server/data/catalog.ts#L392)。

直接影响：5,237 条无坐标记录无法进入第二层 AI 召回，也无法进入“附近未定位记录”的反查路径；但其中精确地址明确的仍可能由第一层关联。因此不能把这批记录全部称为“永远无法匹配”。

### 2.5 AI 辅助搜索目前做到哪里

目前是三种独立用途：

| 用途 | 当前做法 |
| --- | --- |
| 行程理解 | 输入文本 → 千问输出景点顺序、中文搜索词、显式需求 → 前端按固定逻辑搜索地图候选 → 用户选择和确认 |
| 本地身份匹配 | 上述少量 POI 的候选选择 |
| 设施分析与说明 | 每批最多 10 个候选批量分析；按设施推断并生成说明，真实路线数值由服务端补入 |

`/assist/parse` 只接受 `mode: itinerary`；自然语言附近搜索没有入口和对应结构。前端自动查询解析出的地点只是应用预设编排，没有让模型看到地图返回后决定下一次工具调用。

当前 `QwenModel` 只发 `messages + response_format: json_object`，没有 `tools`、工具结果回传或 Agent runner。`JsonModel.complete()` 只返回字符串；对非 `stop` 的结束原因或空 `content` 直接报错，这个接口也不能原样承接正常的 `tool_calls` 响应。仓库的 Agent 开发指南是接入参考，不是已经运行的产品功能。

代码：[parse 路由](../../src/server/routes/assist.ts#L7)、[前端固定地点查询](../../src/client/useItineraryDraft.ts#L220)、[批量分析](../../src/server/ai/service.ts#L256)、[模型调用](../../src/server/providers/qwen.ts#L37)、[依赖](../../package.json)。

## 3. 优化一：相似度召回后一次 LLM 验证

### 3.1 推荐的匹配流程

```text
一批高德厕所 POI
  → 复用有效的既有 POI 关联
  → 对新 POI 多路召回本地记录
      A. 有位置：距离 + 名称/地址
      B. 无位置：区县 + 名称/地址
  → 综合相似度排序，每个 POI 保留少量候选
  → 一次 LLM 请求批量判断这些 POI 各自对应哪条记录
  → 服务端检查 ID、互斥冲突、并发占用
  → 合并本地设施与高德位置，保存关联
  → 无匹配、歧义、失败保留独立高德候选
```

相似度用于缩小验证范围，不直接表示同一实体。按用户期望，新的关联统一进入验证；现有强规则改作特征与冲突检查，不再静默跳过模型。已有效验证并缓存的关联直接复用。

### 3.2 召回和排序怎么改

- 名称保留原文，另存标准化检索文本：统一全半角、空白、常见厕所后缀；规范名称别名及常见地址表达，不删除甲乙门牌、数字和入口差异。
- 名称相似度使用中文字符二元组和编辑距离；地址使用道路、完整门牌、地标、入口等特征，优先保留能辨别身份的信息。拼音/别名可作为附加召回通道。
- 有可靠位置时加入距离特征；坐标系未知的原表位置只作近似线索，不能当精确位置硬判。无坐标不再直接排除，通过区县与文本召回。
- 多路结果合并、去重，再按名称、地址、位置和区县等组合排序；明确不相容的门牌或设施身份保留冲突标记。相同大院可能有多座厕所，不能因为地址相同就强行合并。
- 第一版可用内存区县分组和字符二元组倒排索引；13,124 条数据无需先引入向量数据库。实际延迟用基准测量。以后需要更强持久化/查询时再迁移 SQLite；中文 FTS5 的 tokenizer 和短查询限制需按[官方核对](references.md)选用。
- 语义向量作为评测后的补充：它可以召回别名和语义近似，但“都叫公共厕所”并不是身份相同。不能代替地址、空间和 LLM 验证。

建议试验初值为每个 POI Top-6、首屏验证窗口最多 10 个 POI；这是压测和小样本标注的起点，不是已经证明有效的阈值。缺失字段按可用特征重新计算得分，不将缺失坐标视为最大距离。相似度分数仅供匹配内部使用，不作为游客看到的设施评分或置信百分比。

### 3.3 “一次 LLM”应怎样界定

建议明确为：**对一次匹配窗口中需要新建关联的全部 POI，合并为一次模型验证请求；每个候选不单独请求。** 有效缓存命中或没有可召回记录时为零次。后续用户加载更多属于新的窗口；若希望整个查询只允许一次，则剩余 POI 先保留独立结果并延后验证，不隐式拆出多次请求。

匹配验证的示意契约：

```ts
// 仅示意待实现接口。
verifyMatches({
  items: [{ poiId, poiFacts, candidates: [{ localId, fields, features }] }]
}) => {
  items: [{
    poiId,
    localId: string | null,
    decision: "match" | "no_match" | "ambiguous",
    basisFields: string[]
  }]
}
```

把有限的名称、地址、区县、可用位置及其来源、距离和召回特征给模型；不发送整份台账。检查每个 `poiId` 恰好有一个结论，`localId` 属于它自己的候选集合。不同 POI 抢同一记录时先保留歧义，不用第二次隐藏调用；本地关联发生并发变化时重新检查占用，不能覆盖其他查询刚保存的关系。

严格一次请求意味着此模块禁用自动内容修复和 SDK 自动重试。格式错误或超时就保留地图结果，记录 `validation_failed` / `provider_error`，与业务 `no_match` 分开；其他行程解析和设施分析可保留当前修复行为。这与现有 PRD“最多修复一次”不冲突，零次修复也在上限内。

持久化保存 POI ID、本地 ID、匹配方法、依据摘要和输入版本。缓存键纳入源数据版本、POI 事实、候选快照、匹配/提示词版本及模型标识。成功关联可复用；模型服务错误不缓存为长期“无匹配”。后续分页新建关联也要触发持久化，不能只依赖当前 bootstrap 末尾的保存。

## 4. 优化二：可以迭代调用工具的附近搜索 Agent

### 4.1 框架与模型接入

建议以 **OpenAI Agents SDK for TypeScript** 作为优先验证的框架，用 Chat Completions 模型适配器接入现有千问 client；保留 `DASHSCOPE_API_KEY`、`QWEN_BASE_URL`、`QWEN_MODEL`。框架负责运行循环、消息和工具调用生命周期，业务模块负责地点、资料和路线。官方示例支持自定义 OpenAI client，但项目的实际模型、参数、SDK 版本兼容性需要联调，不因“OpenAI compatible”直接视为全功能通过。详见[官方资料核对](references.md)。

现有 `JsonModel` 继续承载一次性解析/验证/设施分析；新增工具调用模型适配器，返回文本、完整 tool calls、结束原因等信息。不能给现有 `complete(): string` 仅加一个 `tools` 参数就认为 Agent 已完成。若框架与当前依赖不能兼容，可实现同样工具契约的有界原生 SDK 循环，但应明确这是自管运行时。

使用一个附近搜索 Agent 即可，不需要为每个地图/数据库工具再创建一个 Agent。当前 Codex 可用的开发技能和工具也不会自动出现在游客使用的产品里，产品必须显式注册自己的工具。

### 4.2 工具如何划分

以下名称为拟议接口，不是现有工具：

| 工具 | 负责内容 | 有限返回值 |
| --- | --- | --- |
| `get_current_location` | 读取本会话新鲜的定位；缺失时请求前端定位并暂停 | `originId` 或 `requires_client_action`、失败状态 |
| `search_places` | 解析用户给出的地名/入口，调用现有高德文本搜索 | 地点 ID、中文名称、地址及候选歧义 |
| `search_toilet_candidates` | 给确定起点搜索地图厕所，并加入已有位置的本地候选 | `candidateSetId`、有限候选、分页与部分失败状态 |
| `match_local_records` | 对该候选集合召回本地资料，执行上一节的一次批量验证 | 合并后的候选集合、匹配/歧义/失败计数 |
| `rank_toilet_candidates` | 真实算路、设施分析或规则回退、过滤和分组 | 当前 `SearchResult` 结构、结果引用、未完成状态 |

服务端保管 `originId`、`candidateSetId` 对应的坐标和完整记录；工具只接受本会话已经存在的引用和有界参数。模型不能凭空输入一个厕所 ID 或编造坐标；最终页面事实由服务端结果产生。

为支持这种分步调度，先从 `QueryService` 抽出可复用的召回、匹配、路线分组能力，仍让手动搜索调用同一套实现。直接把完整 `/toilets/search` 包成工具也能做基础 Agent，但它内部已经完成匹配；若采用这种封装，就不能再额外调用匹配工具造成重复验证。这里推荐前述分步拆出方案，以满足用户希望观察和迭代搜索过程的需求。

### 4.3 用户示例的实际运行过程

```text
用户：“我想知道当前位置附近的厕所”
  → Agent 识别 nearby 意图，需求沿用已有选择（无已有选择时 any）
  → 调用 get_current_location
      → 有新鲜定位：返回 originId
      → 无定位：暂停 → 前端浏览器授权/定位 → 坐标转换 → 恢复原运行
  → 根据位置结果，调用 search_toilet_candidates
  → 根据返回的 POI 集合，调用 match_local_records
      → 相似度召回 → 一次批量 LLM 验证 → 返回合并结果
  → 调用 rank_toilet_candidates
      → 算路、按需求过滤与排序、形成卡片事实
  → Agent 判断信息是否够用
      → 足够：输出简短说明 + 结果引用，页面显示现有列表/地图
      → 当前批不足：在预算内继续下一页，或建议使用允许的更大范围
      → 定位/地点不明确：请求用户补充起点
```

每次工具返回都进入模型上下文，由模型决定继续、改写地名、选用其他工具或完成，这才是迭代工具调用。匹配模块内部的“一次验证”与外层 Agent 的多轮推理是两种不同预算。

如果每个核心工具分别占一轮，上述无额外补搜的示意流程可有约 5 次编排模型调用（4 次工具选择及最终答复），再加 1 次匹配验证；保留独立设施分析时还会增加调用。缓存、同轮独立工具和工具粒度都会改变次数，不能承诺整条自然语言流程只调用一次模型。匹配验证、设施分析和 Agent 轮次应分别计数并纳入总预算。

### 4.4 定位必须有前后端桥接

LLM 和服务器不能自行读取游客手机位置。浏览器 Geolocation 需要安全上下文和用户授权，返回 WGS84；项目现有转换与北京校验可以复用。Agent 的“自动定位”表示自动发起这一动作，不表示绕过浏览器授权。

拟议运行状态包括 `running`、`requires_client_action`、`requires_user_input`、`completed`、`partial`、`failed`。服务端保存运行 ID、版本、消息历史、待执行的 tool call 和预算；前端提交定位结果时携带该次待办 ID，服务端验证它属于当前运行且未消费，再转坐标、回填工具结果并续跑。具体框架暂停/恢复 API 按实际版本验证，不能将业务运行状态误认为框架已提供所有浏览器交互。

不应长时间挂住一个 HTTP 请求等待用户授权。可以先实现短轮询/显式续跑，后续再增加 SSE。重复提交定位结果不应启动重复搜索；用户修改起点/需求后，旧运行的结果不能覆盖新结果。拒绝授权时转手选起点，不用服务器 IP 假装用户当前位置。

### 4.5 “泛化”的边界和场景

| 用户表达 | 应有行为 |
| --- | --- |
| “我附近的厕所” / “Restroom near me” | 按需定位，沿用需求与范围 |
| “天坛东门附近，要坐便” | 先搜明确地点，不触发无关定位；需求设为 `seated_required` |
| “换一个不用门票的” | 使用上轮起点、结果和排除条件，重新过滤/补搜 |
| “不需要坐便了” | 正确识别否定，更新需求，不重复解析整段行程 |
| “故宫附近”，返回多个入口 | 展示有限地点候选供澄清，不静默假定入口 |
| “这里没有，再远一点” | 使用有界分页/扩展范围；保留原需求和进入条件 |
| 定位拒绝或人在北京外 | 说明情况，允许选择北京起点 |
| “需要轮椅路线/一定有纸” | 理解表达并说明现有筛选不支持，不虚构对应能力 |

泛化优先覆盖既有厕所业务内的意图、工具次序和上下文引用，不顺带扩大为任意联网代理或所有城市搜索。地名、POI 名称和台账备注只作为数据进入模型。

### 4.6 执行预算和结果控制

- 建议起步限制：最多 6 次编排模型请求、10 次工具执行、首屏一个匹配验证窗口。匹配和独立设施分析另计到总模型预算；不是通过工具嵌套绕过上限。这些是待联调初值。
- 每个运行维护累计 POI、路线、模型 token、耗时、工具次数；修复当前 60 条候选限制未累计生效的问题。
- 工具失败和空结果分开；相同参数且结果不变的重复调用终止。供应商限流时服从共享退避，不能靠换关键词连续请求。
- 对一个模型轮次返回的全部 tool calls 执行并逐项回填对应结果；依赖步骤顺序执行，独立步骤才并发。结束时校验完整结果引用，而非看到模型文本就成功。
- 匹配、路线、说明分阶段暴露进度。达到预算仍有有效候选时返回 `partial`，保留手动搜索与已有卡片。
- Agent 可选择如何补搜和如何说明，展示分组、排序、真实路线和原始设施字段仍由现有共用规则控制。

### 必要验收

1. 使用少量固定标注样例区分“真实同一厕所”“相近但不同厕所”“确实无匹配”；覆盖无坐标、异名、相同大院不同入口、甲乙门牌、1号/10号、道路后缀。
2. 分开测召回 Recall@K、最终匹配精确率/召回率、错误合并和歧义率。5,237 条缺坐标记录单列统计；不能用普通相似度分数证明实际匹配正确。
3. 断言一次窗口只有一个验证请求，缓存零次；格式失败无隐藏修复；跨候选 ID、重复占用、并发与重启身份均正确。
4. Agent 使用可控工具记录测试顺序，再用既有千问配置真实联调：缺定位→暂停→恢复→地图→匹配→路线→完成；明确地点、否定需求、多入口、后续条件修改也要覆盖。
5. 定位拒绝、地图空结果/限流、模型失败、重复工具、总预算耗尽仍能给出正确的澄清或部分结果，不回传虚构厕所与路线。
6. 单独统计首批可见卡片耗时与全部说明完成耗时，以及外层编排、匹配验证、设施分析各自的请求数量和成本；目前没有新方案的性能/准确率实测值。
