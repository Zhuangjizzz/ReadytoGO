# ReadytoGo Demo 开发规格与执行计划

Status: ready-for-agent

制定日期：2026-10-09（Asia/Shanghai）。实施进度：执行中，详见 [实施记录](execution.md)。

本规格使用 `to-spec`，根据当前仓库、已确认的 Demo PRD 与范围决策整理。目标是把现有资料、界面原型和 API 联调成果变成可运行的手机网页。本文确定开发顺序、模块边界和验证方法；产品规则仍以当前 PRD 及五份细则为准，来源索引见 Further Notes。

## Problem Statement

北京入境游客在陌生环境中难以快速找到适合自身需求、能够进入且距离可接受的厕所。现有地图位置和公厕资料彼此分散，游客还需要理解中文名称、设施描述、景区进入条件，并把推荐交接给地图导航。需要成人坐便的游客尤其难以判断哪些地方有可用线索。

目前仓库已有需求、原始公厕 CSV、可交互 UI 原型、千问与高德的基础联调证据，以及公网部署验证页；尚未形成真实数据、查询服务、AI 和页面相互配合的产品。原型中的模拟地点、核验文案和旧分组不能直接作为当前产品实现。

本次开发需要在 Demo 范围内完成可重复演示的业务流程，展示数据整理、AI 分析和软件开发能力；不以补齐全市资料、逐条现场核验或生产级治理为前置条件。

## Solution

交付无需登录、默认英文且可切换中文的手机网页，提供两条主要路径：

1. 找附近厕所：定位或手选北京起点，选择无特殊要求或需要坐便，查看分组结果、地图与详情，再打开高德导航或复制中文地址。
2. 规划景点停靠：手动添加或用 AI 辅助解析 1–10 个北京景点，确认地点后按用户顺序逐站推荐，支持替换、跳过、单站重试和刷新恢复。

先清洗现有文件、取得真实地点与路线，复用同一套推荐规则服务附近和规划。AI 负责理解行程、辅助资料匹配、分析设施线索和解释推荐；软件负责位置、路线、分组、排序、交互与保存。真实模型调用属于正常演示主线，模型失败时仍可手动完成流程。

## User Stories

### 进入、语言与起点

1. 作为入境游客，我希望无需注册即可进入手机网页，以便立即开始找厕所。
2. 作为首次访问的游客，我希望默认看到英文界面，以便理解主要操作。
3. 作为使用中文的游客，我希望切换中文并保留显式语言选择，以便下次继续使用熟悉的语言。
4. 作为游客，我希望切换语言时保留起点、需求、行程和选择，以便不必重新操作。
5. 作为游客，我希望看到英文辅助名、中文原名和中文地址，以便识别地点并向他人询问。
6. 作为游客，我希望在首页选择找附近厕所或规划行程，以便按当前情境进入正确流程。
7. 作为游客，我希望点击找附近厕所时获取当前位置，并可以修改起点，以便按实际出发位置查询。
8. 作为定位失败的游客，我希望通过地点搜索或地图选点继续操作，以便不受定位拒绝、不支持或超时影响。
9. 作为定位精度较差的游客，我希望知道当前是大致位置，并能继续或重选，以便自主决定查询起点。
10. 作为游客，我希望地点候选显示名称、区县和地址，并由我选定具体结果，以便区分同名地点。
11. 作为选择北京以外地点的游客，我希望得到选择北京地点的提示，以便理解当前 Demo 的服务范围。

### 附近搜索与推荐

12. 作为游客，我希望在无特殊要求和需要坐便之间单选，并沿用上次选择，以便得到符合需求的结果。
13. 作为需要坐便的游客，我希望同时看到资料明确记载和设施线索推断的候选及其依据，以便判断可尝试的地点。
14. 作为游客，我希望明确没有成人坐便、仅有儿童坐便或材料冲突不会被解释为已具备成人坐便，以便理解信息的实际含义。
15. 作为游客，我希望从默认 10 分钟扩大到 20 分钟步行范围，以便在近处选择不足时继续查找。
16. 作为需要坐便的游客，我希望仍能查看超出步行时限的有线索候选，并把扩展召回从 5 公里增加到 10 公里，以便权衡更远的选择。
17. 作为需要坐便的游客，我希望主动展开普通厕所，以便在缺少坐便线索时仍有其他选择。
18. 作为游客，我希望区分范围内、更远、其他附近、需门票或消费、路线未知的结果，以便理解各候选的使用条件。
19. 作为游客，我希望门票或消费地点默认独立展示，并可通过开关纳入普通排序，以便按自己的进入条件选择。
20. 作为游客，我希望附近搜索避开资料显示不可用或预计当前关闭的地点，同时保留开放信息未知的候选，以便继续查找。
21. 作为游客，我希望看到真实路线的步行时间和距离，路线未知时得到明确说明，以便不把直线距离误当步行时间。
22. 作为游客，我希望始终看见结果的计算起点，以便分清当前距离是从哪里出发。
23. 作为游客，我希望先浏览列表，按需打开地图，并让卡片和地图点相互选中，以便兼顾阅读和位置判断。
24. 作为游客，我希望查看厕所详情、设施来源、进入说明和简短推荐理由，以便决定是否前往。
25. 作为游客，我希望已有结果先出现，并能加载更多候选，以便不必等待全部外部请求结束。
26. 作为游客，我希望无合适候选、没有候选和查询失败采用不同提示，并提供扩大范围、换起点或重试入口，以便知道下一步能做什么。
27. 作为快速调整条件的游客，我希望旧请求不覆盖新结果，返回列表时保留筛选和滚动位置，以便继续比较。

### 景点规划与逐站操作

28. 作为游客，我希望按顺序添加 1–10 个北京景点，并可删除、更换和重排，以便表达自己的游览计划。
29. 作为游客，我希望重复添加地点时收到一次提醒并能选择继续，以便保留确实需要重复停靠的安排。
30. 作为大型景点的游客，我希望可选具体入口、集合点或景点位置，以便让该站查询起点更贴近计划。
31. 作为游客，我希望每站看到一个主推荐和最多两个备选，并可打开该站完整列表，以便先快速决策再深入比较。
32. 作为提前规划的游客，我希望周期开放的地点不会因查询时闭馆而消失，同时能查看营业时间，以便在未来游览时参考。
33. 作为游客，我希望各站独立加载，成功站先可操作，失败站可以单独重试，以便局部故障不阻断整个行程。
34. 作为游客，我希望替换某站厕所，或只跳过该站厕所安排而保留景点，以便保留自己的选择。
35. 作为游客，我希望调整顺序时保留站点及选择，更换某站起点时只重算该站，以便避免无关结果被重置。
36. 作为游客，我希望修改全局需求或进入条件后重算各站，并在旧选择失效时收到提示，以便继续使用符合条件的安排。
37. 作为游客，我希望同一厕所在不同景点附近时仍可分别出现，以便每站都能使用适合自己的候选。
38. 作为已到达某站的游客，我希望点击从当前位置查找，进入重新定位的附近搜索，以便按现场位置行动。

### AI 辅助

39. 作为游客，我希望粘贴不超过 2,000 字符的中英文行程，让 AI 提议地点检索词和显式需求，以便减少手动录入。
40. 作为游客，我希望 AI 保留景点原文顺序，不擅自添加地点，时间只作为文字备注，以便遵循我的行程意图。
41. 作为游客，我希望未表达需求时沿用当前选择，而“不需要坐便”正确映射为无特殊要求，以便避免偏好被误改。
42. 作为游客，我希望在确认前编辑同名、未匹配、重复或超过 10 站的结果，并保留原行程，以便修正后再替换。
43. 作为提出额外需求的游客，我希望知道当前不支持哪些专门筛选，以便不把未实现能力当作查询条件。
44. 作为游客，我希望推荐说明使用当前语言，并基于本次候选的设施、路线和进入信息，以便理解为何推荐。
45. 作为游客，我希望 AI 失败时保留输入、已有结果和选择，继续手动编辑或使用规则说明，以便完成原有任务。

### 导航、询问与保存

46. 作为游客，我希望从卡片或详情打开高德 App、网页路线或复制中文名称地址，以便选择可用的导航方式。
47. 作为游客，我希望选择从当前位置或搜索起点导航，并在更换起点后更新距离和时间，以便获得正确路线。
48. 作为没有当前位置或目的地坐标的游客，我希望使用已选起点，或继续查看详情、复制地址和手动地图搜索，以便仍能行动。
49. 作为地图加载或 App 唤起失败的游客，我希望列表、网页入口和地址文本继续可用，以便不被单一入口阻断。
50. 作为语言不通的游客，我希望打开五句固定双语询问卡，以便询问成人坐便、开放、游客使用、入口和卫生纸。
51. 作为需要向工作人员展示手机的游客，我希望询问卡中文大字在上、英文在下，支持前后切换、返回和横屏，以便让对方容易阅读。
52. 作为游客，我希望刷新后恢复一份当前行程及需求、进入设置、每站选择和跳过状态，以便接着使用。
53. 作为游客，我希望清除当前行程时删除相关结果缓存和选择，并可保留语言，以便重新开始。
54. 作为浏览器存储不可用或旧版本状态无法恢复的游客，我希望仍能继续操作，以便不因保存失败而无法使用。
55. 作为游客，我希望浏览器定位仅用于当前会话，手选景点可随行程保存，以便区分临时位置与主动保存的内容。

### 数据与演示交付

56. 作为 Demo 开发者，我希望现有 CSV 可重复导入，保留稳定 ID、来源行和原始字段，并区分零与缺失，以便得到可查询且可说明来源的数据。
57. 作为 Demo 开发者，我希望本地资料和高德地点自动关联、明确重复项归并，无法匹配时保留独立候选，以便用现有覆盖继续开发。
58. 作为 Demo 展示者，我希望用实际数据处理结果及真实模型输入、结构化输出和页面结果说明流程，以便展示项目完成了什么。
59. 作为 Demo 展示者，我希望供应商故障时可用明确标注的缓存或样例继续讲解，以便展示不中断且不混淆真实调用结果。
60. 作为后续开发者，我希望拿到依赖、启动与配置说明、必要测试、数据处理记录和已知限制，以便复现、维护和继续迭代。
61. 作为 Demo 展示者，我希望至少在一个实际手机浏览器跑通主线并检查导航降级，以便交付可操作的手机网页。

## Implementation Decisions

以下区分已确认的产品约束与本计划采用的工程默认值。后者用于直接启动实现，可在不改变外部契约和范围的前提下简化调整，不另起选型或资料治理项目。

### 1. 应用结构与模块边界

- 新建 React + TypeScript + Vite 前端与 Node.js + TypeScript 服务端。采用单服务部署，提供前端构建产物、业务 JSON API 和健康检查；开发时可分别启动前后端。沿用已有 Node HTTP 服务的运行方式，建立薄路由层，不把验证页描述成已有业务后端。
- 首版采用清洗后的本地 JSON 数据和服务端内存查询，匹配与分析结果使用独立缓存；浏览器保存当前行程。暂不引入数据库服务、账户或云端同步。
- 保持四个职责清楚的模块：数据目录（导入、稳定身份、来源和关联）、查询推荐（召回、路线、规则与规划预览）、AI 辅助（解析、匹配辅助、推断和说明）、网页体验（地点选择、结果、规划、导航及本机状态）。这是代码职责划分，不是四个独立服务。
- 高德和千问接入集中在供应商适配器。附近搜索与逐站规划共用查询推荐模块，通过 `context=nearby/plan_stop` 选择开放规则；卡片与详情不重复实现推荐判断。
- 第一阶段建立依赖锁定、启动、导入、构建、类型检查及必要测试入口。只移植开发辅助脚本中适用的请求逻辑，产品运行不依赖开发技能目录。

### 2. 数据、身份、坐标与自动匹配

- 使用现有 GB18030、多行表头 CSV；一次性导入全部可解析记录，演示先选择少量北京起点联调。原始文件保留，输出规范化数据、导入数、可用位置数、跳过数和简短异常说明；原始记录数不作为最终可推荐数量。
- 区分设施列自身含义，重点检查第三卫生间、无障碍设施、无障碍厕所间、无障碍厕位、管理间与盥洗室；空白/缺失转 `null`，数值 0 保留，备注保存原文。
- 内部稳定 ID 与政府编号、高德 POI ID 分开。重复导入复用身份；相同 POI ID 或明确重复实体合并来源行，不能只按厕所名称或政府编号盲目归并。
- 解析十进制度与合法度分秒，仅按明确模式修复格式或经纬互换。无法可靠使用的位置按名称、地址、区县召回高德地点；原表坐标系不清楚时优先使用匹配位置，不凭空纠正异常数字。
- 查询与导航内部统一 GCJ02，保留 `lng/lat/crs`。高德位置不重复转换，浏览器 GPS 仅在适配器转换一次；设施来源与位置来源可以不同。
- 先查可用本地候选，再补高德；规则自动匹配优先，模糊候选可由 AI 从召回 ID 中选择。不能区分时保持高德独立记录，不强制人工确认或阻断列表。匹配阈值与有限召回条数用少量实际样例确定并记录。
- 保留 `Toilet`、`Source`、`Place`、`Route`、`PlanLocal` 五类对象。原始设施、派生分析和用户选择分别保存；无位置记录保留文字详情，但取得可用路线后才进入步行推荐。

### 3. 推荐规则与计算边界

- 需求仅为 `any` 和 `seated_required`。坐便状态采用 `documented/inferred/unknown/unavailable`；资料记载或推断都可进入坐便推荐。推断保留依据与可能性措辞，不回写为原始事实。
- 明确否定优先于推断；只有儿童坐便不视为成人可用；无法解释的材料冲突归为 `unknown` 并保留简短说明。语言、国籍或同行人不产生额外筛选。
- 普通召回随 10/20 分钟选择使用 2/3 公里直线半径；坐便额外召回 5 公里，可扩至 10 公里。步行资格使用真实路线原始秒数，更远坐便候选不因 10/20 分钟上限隐藏。
- 五个互斥展示组为 `matched/farther/otherNearby/conditionalAccess/routeUnknown`。门票或消费候选默认进入 `conditionalAccess` 并保留 `baseGroup`；开关开启后返回本来分组参加排序。路线未知仍遵守进入条件与普通厕所的主动展开规则。
- `matched/farther` 按步行秒数、步行米数、稳定 ID 排序；无路线按直线距离。路线状态采用 `success/unreachable/provider_error/pending`，失败数值为 `null`；明确步行不可达不进入步行推荐。
- 根据 `Asia/Shanghai` 处理可解析营业时间和简单跨午夜时段；复杂规则显示原文。撤销、永久关闭或禁止游客的记录排除；附近另排除当前预计关闭，规划保留周期开放地点。开放与进入信息未知可保留。
- 单站主推荐取 `matched` 第一条，最多两个备选，更多候选进入该站完整列表；无 `matched` 时明确没有范围内主推荐，更远和其他候选供用户选择，不能冒充范围内匹配。
- 展示分钟向上取整且至少 1 分钟；筛选不使用展示分钟。距离展示米或一位小数公里；无路线时只展示直线距离或步行时间暂不可用。AI 和用户手选不改变规则排序或路线值。

### 4. API、并发与失败语义

业务前缀采用 `/api/v1`，语言为 `en/zh-CN`，使用当前 PRD 的对象与枚举。接口职责如下：

| 接口 | 契约与主要职责 | 首次交付 |
| --- | --- | --- |
| `GET /places/search` | 接收关键词、语言和北京范围；返回可选地点与 `hasMore`，默认最多 10 条 | 阶段 1 |
| `POST /toilets/search` | 接收起点、上下文、需求、步行限制、进入设置、扩展半径、语言、`queryVersion` 与游标；返回分组候选、分析状态及分页信息 | 阶段 1 最小闭环，阶段 2 补齐规则 |
| `GET /toilets/:id` | 返回厕所详情、来源字段与当前语言分析说明；不存在返回 404 | 阶段 2 |
| `POST /navigation/link` | 接收厕所 ID 与导航起点；返回 App/网页入口、目的地、复制信息，以及本次起点对应的 `routeStatus/walkSeconds/walkMeters`；缺目的地坐标不生成错误路线链接 | 阶段 2 |
| `POST /plans/preview` | 接收带稳定 `stopId` 的站点、全局条件和 `revision`；返回逐站状态、主推荐、备选与整体状态 | 阶段 3 |
| `POST /assist/parse` | 接收文本、`mode=itinerary`、语言与当前需求；返回待确认的景点检索词、显式需求和提示 | 阶段 4 |

- 成功封装 `requestId/data/warnings`；失败封装 `requestId/error.code/error.message/error.retryable`。输入格式错误为 400，北京外或未选定地点为 422；供应商失败使用可重试错误或部分结果。
- `data.status=complete/empty/partial` 表达查询处理状态；是否满足需求由分组表达。无匹配、无候选和整体服务失败不得共用一个空数组表示。
- 搜索游标绑定查询条件。条件变化重新查询，旧 `queryVersion` 无权更新当前结果；行程响应按 `stopId` 关联，旧 `revision` 无权覆盖编辑后的行程。站点计算键由 `stopId`、起点及有效查询条件组成，与展示顺序分开；重排后以新 `revision` 补拉仍在加载站点的已有计算/缓存，不重新算路。AI 补充结果也受同样版本与计算键约束。
- 采用普通 HTTP 有限批次与按需短轮询补齐结果。同一标准化条件与原游标标识同一批次，重复读取复用在途计算或结果快照；下一游标用于用户加载下一批，按厕所 ID 合并，避免重复追加。切换条件或离开页面停止等待旧请求。
- 本计划补充响应字段 `pendingWork`，表示当前批次是否仍有在途工作，与 `partial` 和 `hasMore` 分开。只有 `pendingWork=true` 才自动补拉；达到本批次总等待上限后终止等待，未完成项转为失败或回退。终态 `partial` 不自动重试供应商；用户显式重试开启新一轮有界尝试并复用成功结果。第一阶段确定等待上限与显式重试入参，集中配置并覆盖测试。
- 多站通过同一预览契约独立计算、独立更新；客户端可按站提交预览请求，成功站先展示，单站重试不清空其他站。请求版本判断不能只依赖取消网络请求。
- 保留工程初值：定位 8 秒、外部服务 5 秒、AI 12 秒；路线缓存 15 分钟；每批算路 10 个、每起点每次最多 60 个、并发初值 5。多站共享供应商并发上限，避免每站各占满并发。达到本次 60 个上限即结束自动处理；仍有未消费候选时返回 `hasMore=true/nextCursor`，由用户加载更多启动下一次有界处理。召回已耗尽则为 `false/null`；失败记录不能作为永远不前进的下一页。
- 路线缓存键至少包含起点、终点、坐标系和步行模式；查询/分析缓存还包含需求、上下文、进入设置、范围、语言和相关数据版本。缓存期限是工程参数，不是设施可信度门槛。

### 5. 页面、规划、本机状态与导航

- 提供首页、附近结果、共用地点选择器、厕所详情、行程编辑、行程结果及询问卡。复用原型的布局、颜色、卡片与触控反馈，按新 PRD 替换旧文案、分组和模拟接口；视觉最终方向按设计约定执行。
- 列表优先，地图按需加载，卡片和地图点双向联动；条件、计算起点与加载状态持续可见。地图失败保留列表，返回列表恢复滚动位置。
- 行程编辑使用稳定 `stopId`，相同地点可属于不同站。重复提醒可继续；重排只改顺序，不重跑路线，仍加载的站点按新版本接续读取；换站点位置只刷新该站，全局需求/进入条件改变则重算所有站。保留仍适用的选择，对失效选择提示重选，跳过只影响厕所安排。
- 预览结果与用户主动选择分离，异步补齐不能自动覆盖用户刚做的替换或跳过；站点完整列表始终保持 `plan_stop` 上下文。
- 按 `PlanLocal.schemaVersion` 保存一份当前行程、语言、需求、进入条件、站点选择和跳过状态。浏览器定位不持久化；行程清除同步清理相关缓存和选择，可留语言。存储错误退到内存，未知版本提示重建而不锁住界面。
- 导航提供 App、网页和中文地址文本。起点可选当前位置或搜索起点；改变起点通过导航接口调用共用路线能力，使用返回的新路线状态、秒数与米数替换导航区数字。重算失败清除旧数字并显示路线暂不可用，仍保留可用的链接和地址。无定位退回已选起点，无目的地坐标提供文字和地图搜索；有坐标即可交接导航，不添加二次审核步骤。
- 五句询问卡按 PRD 原文随应用打包；中文在上、英文在下，主句建议至少 28 px、触控区至少 44 px，支持前后句、返回和横屏。

### 6. AI 接入与真实演示

- 使用基础 `openai` SDK 接入项目既有千问配置 `DASHSCOPE_API_KEY/QWEN_BASE_URL/QWEN_MODEL`，沿用已有地域设置。
- 首版采用应用先取数、再调用模型分析的流程。行程解析与候选分析分别定义输入输出，不要求所有查询经过多轮工具调度。仅在实际需要时增加受限工具调用，工具只在服务端执行。
- 行程输入最多 2,000 字符，输出中文检索词与原文顺序；模型不生成最终坐标。地点搜索结果由用户确认，超 10 站、同名或未匹配均保留编辑入口，未确认不覆盖原行程。未表达需求为 `null`，否定坐便为 `any`。
- 候选分析批量提供 ID、设施字段、已有坐便状态、路线和进入信息，避免每张卡片单独阻塞一次请求。AI 辅助匹配只能选择召回 ID；设施推断只接受 `inferred/unknown/null`，保留资料明确的肯定和否定。
- 新设施推断经校验后交由共用规则重新形成分组和排序；模型本身不输出最终排序。先显示已有候选，随后补充分析，`analysisStatus` 使用 `pending/complete/fallback`，同时保留用户选择。
- 检查 JSON 类型、枚举、长度、候选 ID 及依据字段；数字、坐标与路线取服务端数据。输出无效最多修复一次，并受总耗时限制；仍失败则保留输入、候选和选择，使用规则说明，允许手动规划。
- 用户文本、地点名与备注按数据处理，不执行其中的命令或任意链接。日志不记录密钥、完整用户行程或精确位置；展示记录仅使用少量脱敏或专门编写的演示输入、输出、页面结果和耗时。

### 7. 配置、部署与接入依赖

- 复用已有地图 Web 服务与模型变量；业务服务需要自己的长期服务端配置。历史本机/服务器临时联调成功不代表长期服务已配置，也不代表额度、延迟或当前可用性已经保证。
- 内嵌地图采用高德静态地图真实底图，由服务端使用现有 Web 服务 Key 请求并校验图片；浏览器提供缩放、平移、选点及卡片标记联动。该接口已实测可用，替代原计划新增 JS API Key 的工程假设。Key 不下发，保留高德署名，按真实标记校准像素投影、CSS 缩放及反向选点；加载失败保留列表。
- 复用现有独立服务、备份、上传、健康检查与回滚流程。正式部署时核对目标 Node 版本、端口及 Linux 依赖，更新构建、启动与配置说明；发布包排除本机依赖、密钥和本地日志。
- 沿用当前公网 IP＋端口的部署方向，域名与 HTTPS 保持后续项。该环境优先演示手选起点与定位不可用时的回退；真实自动定位在满足浏览器安全上下文的环境验证，并单独记录环境限制，不把公网 HTTP 连通当作定位验证。

## Testing Decisions

### 测试入口与现有先例

主测试入口选业务 HTTP API：通过公开请求和响应观察正式导入数据、地点匹配、候选查询、规划与 AI 回退的外部行为。使用同一应用创建入口，在供应商边界替换高德、模型与时钟，避免对内部 helper、组件层级、函数调用次数或私有实现逐层 mock。

数据测试先通过正式导入入口生成临时数据，再由业务查询/详情接口检查结果及导入摘要；不为了测试拆出新的领域服务。页面独有的异步覆盖、编辑确认和本机恢复，用少量浏览器流程测试补充。测试工具可采用 Node 内置测试运行器与 Playwright，第一阶段固定运行命令；不追求覆盖率指标或大规模截图快照。

现有先例只有部署验证页的 HTTP 检查记录，以及供应商连通性输出。前者可参考状态码、资源与健康检查方式，后者可参考真实返回形状；两者均不等于可复用的产品回归套件。测试边界是本计划的工程建议，不声称此前已由用户确认。

### 页面与真实服务验收

- 按 PRD 四步演示主线重复操作：数据进入应用 → 附近搜索与坐便切换 → 中英行程解析及逐站操作 → 导航、询问卡与刷新恢复。
- 使用少量固定北京起点验证真实地点搜索、自动关联、步行路线、地图选点与导航；模型正常路径保留真实解析和候选分析记录。样例用于重复演示，不限制产品只能搜这些景点。
- 浏览器覆盖定位拒绝/超时、地图加载失败、App 不可用、部分路线失败、单站失败、AI 无效输出与存储失败。确认已有有效结果仍可操作，不以错误提示本身出现为完成依据。
- 至少一台实际手机浏览器检查窄屏、中英长文本、地图卡片联动、触控、横屏询问卡与导航降级。记录自动定位测试的实际环境；桌面模拟窄屏不能冒充真机完成。
- 每阶段运行相关类型检查、构建和必要测试；跨阶段规则或接口改变时重跑受影响检查。记录通过项与已知限制，不进行与 Demo 无关的全量审计。

## Out of Scope

- 账号、登录、云同步、历史行程库、反馈后台、实时语音、中英文以外语言与上海等其他城市。
- 轮椅路线、纸巾、亲子等额外筛选；询问卡可问卫生纸，但不因此增加筛选条件。
- 完整交通行程优化、景点顺序自动重排、预计到达时间、定时提醒；输入时间只作文字备注。
- 即时自然语言找厕所和 `mode=nearby` 解析；首版即时搜索由手动控件完成。
- 现场核验、人工审批、证据等级、有效期、营业时间复核周期、正式试点名额和生产级审计。
- 页面数据年份、核验流水、虚构置信百分比或设施评分；不复活原型中的已核验/待核验分组。
- 等待新增 XLSX、补齐全市资料、逐条人工匹配、全量翻译与全量坐标系研究。
- 通用 Skill/Agent 平台、多轮调度强制入口、分布式任务系统、高并发平台与独立数据库基础设施。
- 域名与 HTTPS 的本轮配置、其他远程服务改造和讲解视频录制；视频由用户自行录制。

### 开发阶段与依赖

阶段 1 的执行顺序：

1. 建立最小应用工程、同域 API、配置读取和 HTTP 测试入口，冻结共用数据对象及响应封装。
2. 实现 CSV 导入、稳定 ID、来源字段与初始设施状态，生成可查询 JSON 和导入摘要。
3. 接入北京地点搜索、本地召回、规则匹配、高德补充和真实步行路线，建立有界批次与版本字段。
4. 以最小地点选择器和结果列表串起真实查询；记录一个实际北京起点的成功结果及部分失败回退。

阶段 2 的执行顺序：

1. 完成坐便、范围、进入和开放规则，覆盖分组与秒数边界测试。
2. 将原型组件迁入产品，补齐默认英文、中文切换、状态提示、详情与列表返回行为。
3. 接入真实定位、手选/地图选点与地图卡片联动，校准真实底图上的标记与反向选点，处理失败回退。
4. 完成导航起点选择及重算、网页/App/复制入口和固定询问卡，验证单起点端到端流程。

阶段 3 的执行顺序：

1. 建立行程编辑状态、稳定 `stopId` 与 `revision`，完成站数、重复地点和顺序操作。
2. 通过共用查询生成逐站预览，补齐主推荐/备选/完整列表与独立加载、失败重试。
3. 实现替换、跳过、条件变化后重算与选择有效性判断，防止旧响应覆盖用户操作。
4. 实现本机保存、刷新恢复、清除和存储回退，验证 1 站、多站及上限场景。

阶段 4 的执行顺序：

1. 用既有千问配置接入 SDK，固定解析和候选分析 schema、输入限长、超时及一次修复。
2. 完成解析结果到高德地点候选的映射与待确认编辑；确认后才替换行程。
3. 补充模糊资料匹配辅助、设施推断、英文辅助名与当前语言推荐说明，接入版本保护和缓存。
4. 跑中英文、无需求、否定、歧义、超站数与失败样例，保存少量真实调用和页面对应记录。

阶段 5 的执行顺序：

1. 跑完整主线和必要异常，修复阻断问题，核对全部用户故事与 Demo 验收条目。
2. 按现有流程准备并部署业务构建、数据和服务端配置，检查页面/API/健康检查，记录版本及回滚位置。
3. 在实际手机浏览器完成主线、窄屏和导航降级检查，说明公网 HTTP 的定位限制及可用的手选路径。
4. 整理启动与依赖说明、无凭据配置例、数据处理摘要、AI 调用示例、功能检查结果、已知限制和简短演示步骤。

可以并行的工作：阶段 1 固定契约后，数据/查询与页面组件可并行；阶段 2 的导航、询问卡可独立推进；阶段 3 期间可准备阶段 4 的 SDK 适配器和固定样例。推荐规则、API schema 与共享行程状态由一个负责者协调，避免各页面自建不同规则。
