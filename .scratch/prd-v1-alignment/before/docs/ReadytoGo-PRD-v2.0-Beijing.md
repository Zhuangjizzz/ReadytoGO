# ReadytoGo 产品需求

状态：已收拢，可据此开展实现。确认日期：2026-10-09。本文与 `prd/` 下五份细则共同构成产品需求；[决策记录](../.scratch/prd-restructure/spec.md)用于追溯。

## 产品目标

帮助入境游客在北京东城区、西城区表达如厕需要，找到合适的附近厕所，查看设施依据，并完成步行导航和现场询问。

## 开发范围

| 能力 | 要开发的内容 |
| --- | --- |
| 手机网页 | 无需登录；英文、日文、韩文界面，始终保留中文地点名和地址 |
| 首页输入 | 一句话描述情况并查询；同时提供无需打字的一键急需和快捷标签 |
| 起点 | 点击查询时获取定位，或由用户确认真实地点作为起点 |
| AI 搜索 | 解析需求并调用高德工具，搜索周边厕所的名称、位置与可用信息 |
| 本地资料匹配 | 用高德厕所名称检索本地厕所名称，召回语义相似度高的几条记录，再由 AI 判断其中是否有大概率属于同一厕所的记录 |
| 推荐与详情 | AI 在满足硬性要求的候选中选择、排序、解释；服务端校验事实与条件 |
| 结构化渲染 | AI 输出结构化结果，网页展示首选、备选、详情、来源和操作入口 |
| 需求微调 | 修改需求后继续查询或重新推荐，变更可见并可撤销 |
| 现场使用 | 高德网页步行导航、固定多语询问卡和如厕贴士 |
| 故障回退 | 保留已获得的可靠结果；AI 不可用时直接查询本地资料并展示基础列表 |

语言负责界面和贴士，不用于推断坐便、设施或行动需求。没有输入需求时按附近查找，有已保存的显式偏好时使用该偏好。

## 主流程

1. 用户输入情况或点击一键急需，提供有效起点。
2. AI 理解需求并调用高德，取得周边厕所。
3. 以每个高德厕所名称进行本地名称语义检索；AI 阅读召回的几条资料，选择大概率对应的记录并取得详情。
4. AI 根据用户需求组织推荐顺序和理由，输出结构化结果。
5. 服务端校验后，网页渲染卡片；用户可以改需求、看详情、打开导航或询问卡。

## 事实边界

- 设施、来源和步行耗时引用真实查询结果；坐便线索保留“未现场核实”。
- AI 的推荐满足用户明确的硬性要求；“不能蹲”不能因距离近而被放宽。
- 实时开放、卫生、厕纸和路线无障碍不作为已核实事实。
- 查询无结果、覆盖受限与服务失败分别表达。

## 实现与交付

交付完整可运行网页及其必要服务、启动说明和验证记录；讲解视频由用户自行录制。

本地匹配的算法、相似度阈值、召回条数和 AI 判断细节在实施中通过样例确定。它们是实现选择，不增加产品范围或独立交互；具体边界见 [AI 契约](prd/ai.md#实现选择)。

同一规则只在对应细则中维护；改动行为时同步接口与验收。两份[原始产品资料](../.scratch/prd-restructure/sources/README.md)仅用于追溯。
